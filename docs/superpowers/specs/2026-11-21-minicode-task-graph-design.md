# MiniCode 持久任务图设计

日期：2026-11-21
状态：用户已确认设计，待审阅规格
目标版本：MiniCode 持久任务图 v1

## 1. 背景

MiniCode 当前使用 `TodoWrite` 保存一份覆盖式待办清单。它适合短任务的进度提示，但不能表达任务之间的依赖关系，也不能可靠区分“现在可以开始”“被其他任务阻塞”和“已经完成并留有证据”这三种状态。

本设计新增一个由模型直接操作的最小持久任务图。模型通过工具创建、推进和查看任务；系统负责持久化、状态流转和依赖校验。首版目标不是实现完整的团队任务调度器，而是补齐 Agent 的任务规划与恢复能力。

## 2. 目标

1. 模型可以通过工具直接创建和推进任务；
2. 任务状态在多个回合和新会话之间持久化；
3. 任务支持显式依赖，未满足依赖的任务不能开始；
4. 任务状态遵循确定的状态机，不接受跳级完成；
5. 当前任务图作为长任务锚点，经过上下文压缩后仍然保留；
6. 任务图在主 Agent 与子 Agent 之间共享；
7. 损坏的任务文件不会被静默覆盖。

## 3. 非目标

- 不实现负责人认领、租约或并发抢占；
- 不实现优先级、截止时间和时间估算；
- 不实现依赖关系修改或任务删除；
- 不实现后台执行、定时调度或自动推进任务；
- 不实现 Web 或终端任务可视化管理界面；
- 不替代 `TodoWrite` 的短清单能力；
- 不支持多个 MiniCode 进程同时写同一任务图；
- 不把任务图状态等同于任务真实完成，外部验收仍是完成判断的最终依据。

## 4. 方案选择

### 方案一：只做外部命令行看板

实现最简单，但任务推进仍依赖人工操作。面试时只能说明“增加了任务文件”，不能证明 Agent 具备任务规划、依赖检查和状态恢复能力。不采用。

### 方案二：模型管理的最小任务图

新增三个模型工具，任务保存为项目内 JSON，系统执行依赖和状态校验。功能足以形成规划闭环，代码量和测试成本可控。采用此方案。

### 方案三：迁移编码 Agent 项目的完整任务系统

包含负责人认领、任务协议、后台执行、团队协作和恢复队列。能力更完整，但会把当前改动扩展成新的调度子系统，超出本轮目标。不采用。

## 5. 总体架构

```text
capabilities/task_graph.py
  ├── TaskGraphStore        任务图读取、校验、原子写入
  ├── TaskCreateTool        创建任务
  ├── TaskUpdateTool        推进任务状态
  └── TaskListTool          查看任务图

main.py
  ├── 创建项目级共享 TaskGraphStore
  ├── 向主 Agent 注册三个任务工具
  ├── 向子 Agent 注册同一组任务工具
  └── 将任务图摘要注入系统提示词动态段

core/agent_loop.py
  └── 任务工具成功执行后登记最新快照，供压缩层保留

capabilities/compression.py
  └── 复用现有任务锚点机制，不在压缩时丢弃任务图
```

`TaskGraphStore` 只负责持久化和状态规则；工具只负责参数校验与格式化输出；Agent Loop 不解释业务依赖，只登记工具返回的任务图快照。

## 6. 持久化模型

任务图保存到项目工作目录下的 `.minicode/tasks.json`：

```json
{
  "version": 1,
  "tasks": [
    {
      "id": "task_1a2b3c4d",
      "subject": "实现任务存储",
      "description": "支持读取、校验和原子写入",
      "status": "in_progress",
      "blocked_by": [],
      "result": "",
      "created_at": "2026-11-21T10:00:00+00:00",
      "started_at": "2026-11-21T10:01:00+00:00",
      "completed_at": null
    }
  ]
}
```

规则：

- 每个任务 ID 使用 `task_` 加 8 位随机十六进制字符；
- `subject` 必填，去除首尾空白后不能为空，最长 200 字符；
- `description` 最长 4,000 字符；
- `result` 最长 8,000 字符，用于记录完成结果或验收证据；
- `blocked_by` 只能引用创建时已经存在的任务；
- 因为依赖只能指向已有任务，图在构造上保持无环；
- 写入先落到同目录临时文件，再使用 `os.replace` 原子替换；
- 同一进程内的读写使用 `threading.RLock` 串行化；
- JSON 无法解析、结构不合法或版本未知时 fail-closed，不自动清空或重建；
- 未完成任务的顺序按创建时间保持不变。

## 7. 状态机

允许的状态：

```text
pending -> in_progress -> completed
```

约束：

1. 新任务只能处于 `pending`；
2. `pending -> in_progress` 要求所有 `blocked_by` 任务均为 `completed`；
3. 只有 `in_progress` 可以进入 `completed`；
4. 不允许 `pending -> completed`；
5. 不允许从 `completed` 回退；
6. 对同一目标状态重复更新是幂等成功，不重复修改时间戳；
7. 尝试执行其他跳转时返回明确错误，不修改文件；
8. 完成任务时 `result` 可以同时写入；若未提供则保留原值。

任务图本身不代表任务真实完成。模型使用 `TaskUpdate(status="completed")` 只表示任务规划层已收口；若启用了外部验收，验收失败仍必须阻止主任务报告完成。

## 8. 工具接口

### 8.1 `TaskCreate`

输入：

```text
subject: string
description: string = ""
blocked_by: string[] = []
```

行为：

- 校验标题、说明和依赖；
- 创建 `pending` 任务；
- 持久化后返回新任务 ID 和当前任务图快照。

### 8.2 `TaskUpdate`

输入：

```text
task_id: string
status: "in_progress" | "completed"
result: string = ""
```

行为：

- 校验任务存在；
- 校验状态转换和依赖；
- 更新时间戳与可选结果；
- 持久化后返回当前任务图快照。

不提供编辑标题、说明和依赖的接口。若计划发生变化，应创建新的后续任务，而不是改写历史。

### 8.3 `TaskList`

输入：

```text
include_completed: boolean = false
```

行为：

- `TaskList` 为只读、并发安全工具；
- 默认显示未完成任务；
- 标记每个未完成任务是 `ready` 还是 `blocked`；
- 可选包含已完成任务；
- 输出末尾给出 `ready / in_progress / blocked / completed` 数量。

## 9. Agent 接入

### 9.1 工具注册

`main.py` 在 `_build_tools()` 中创建一个项目级共享 `TaskGraphStore`：

- 主 Agent 获得 `TaskCreate`、`TaskUpdate`、`TaskList`；
- `workspace_tool_factory` 为子 Agent 注入同一存储实例；
- 子 Agent 即使运行在 Worktree，也读写主项目 `.minicode/tasks.json` 中的同一份任务图；
- 任务图工具不进入隔离文件系统，不随 Worktree 复制。

`TaskCreate`、`TaskUpdate` 声明为非并发安全，避免同一轮多个更新同时修改状态。`TaskList` 可并发执行。

### 9.2 规划模式

`TaskCreate` 和 `TaskList` 加入 Plan 模式白名单，`TaskUpdate` 不加入。规划模式允许模型创建和查看计划，但不能把任务标记为进行中或已完成；否则会出现“代码尚未修改，任务状态已经完成”的语义冲突。切回 Normal 模式后才允许推进任务状态。

### 9.3 系统提示词

`build_system_prompt()` 增加 `task_graph_hint` 动态段，位置在记忆提示之前、Skill 路由之前。内容最多 4,000 字符，只注入：

- 所有 `in_progress` 任务；
- 最多 12 个未完成任务；
- 每项的 ID、状态、标题和阻塞 ID。

已完成任务不自动进入系统提示词，避免上一轮任务的完成记录污染新的用户请求。模型需要查看历史时显式调用 `TaskList(include_completed=true)`。

系统提示词明确：`TodoWrite` 用于临时短清单；存在依赖的多步骤工作必须使用任务图。

### 9.4 压缩锚点

现有 `ContextCompressor.record_task_list()` 继续作为通用任务锚点。主循环在以下工具成功执行后登记其返回快照：

- `TaskCreate`
- `TaskUpdate`
- `TaskList`

这样 Snip、Collapse 和 Autocompact 都能保留最新任务图。任务图写入磁盘是真相来源，上下文中的锚点只是加速恢复和防止目标漂移。

### 9.5 新会话恢复

任务图由项目路径决定，不依赖 `LoopState`。启动新会话时：

1. 读取 `.minicode/tasks.json`；
2. 文件不存在时视为空任务图，不创建文件；
3. 文件损坏时向终端输出一次明确警告，并在系统提示词动态段注入 `[Task graph unavailable: <原因>]`；系统提示词工厂不得因任务图损坏而中断启动；
4. 有效任务图在系统提示词动态段中恢复。

## 10. 错误处理

- 空标题、超长文本、未知依赖：抛出参数错误，模型收到工具错误并修正；
- 未知任务 ID：返回明确错误；
- 依赖未完成：拒绝开始，并列出阻塞任务；
- 非法状态跳转：拒绝更新，当前状态保持不变；
- JSON 损坏：系统提示词注入不可用警告，任务工具抛出“任务图损坏”错误并禁止覆盖；
- 原子写入失败：保留旧文件并返回错误；
- 格式化输出不包含说明正文，避免把任务描述变成第二份上下文。

14. 系统提示词只注入未完成和进行中任务，不自动注入已完成任务；
15. 损坏任务图在系统提示词中显示不可用警告，且不被覆盖。

## 13. 验收标准

1. 三个新工具在主 Agent 中可用；
2. 子 Agent 能读取并推进同一任务图；
3. 依赖和状态规则在存储层强制执行；
4. 重启后未完成任务可恢复；
5. 任务快照经过三种压缩后仍然存在；
6. 规划模式可以创建和查看任务，但不能推进任务状态；
7. 损坏文件 fail-closed；
8. 原有 TodoWrite 行为不变；
9. 新增测试和全量测试通过；
10. 文档只在实现与验证完成后更新。

## 14. 真实性边界

允许的表述：

- 新增模型可直接操作的持久任务图；
- 支持依赖校验、状态机、跨会话恢复和压缩锚点；
- 任务图与子 Agent 共享，但当前不包含认领与租约。

禁止的表述：

- 支持多进程并发调度；
- 支持自动分配任务或后台自动推进；
- 任务标记完成等价于外部验收通过；
- 已实现完整团队任务协议。
