# 记忆注入的消融实验：两次尝试与失败原因

> 结论先说：**这一版消融给不出稳定结论，不能拿它的数字对外讲。**
> 但失败原因很有价值 —— 它同时也是"记忆什么时候才有用"的答案。

## 设计

夹具项目里放一个 conftest：不按"团队约定"准备环境就拒绝运行；
记忆库预置那条约定（两组完全相同）；同一批任务跑两组，唯一差别是**是否注入记忆**。
指标：平均回合数、工具错误数、pytest 通过率、token。
脚本：`benchmarks/memory_ablation.py`；存档：`benchmarks/memory_ablation.json`。

## 两次实跑的结果（互相矛盾）

| 轮次 | 组 | 平均回合 | 工具错误 | pytest 通过 |
|---|---|---|---|---|
| max_turns=5（4 任务） | 不带记忆 | 4.8 | 1 | **0/4** |
| | 带记忆 | 5.0 | 0 | **2/4** |
| max_turns=8（4 任务） | 不带记忆 | 6.2 | 0 | **2/4** |
| | 带记忆 | 6.8 | 2 | **3/4** |

第一轮看起来"记忆把通过率从 0/4 提到 2/4"，第二轮这个差异缩到 2/4 → 3/4，
而且注入组的工具错误反而更多。**两次结论不一致 = 这个测量装置还不可靠。**

## 三个原因（都查清了）

1. **约定仍然"可从仓库推导"**。第一版把变量名写在报错信息里 —— 控制组读一眼 conftest
   就自己修好了。第二版把报错里的变量名去掉了，但 **conftest 源码里仍然有
   `os.environ.get("MINICODE_OFFLINE")`** —— agent 读一遍文件就知道要设什么。
   第二轮里模型正是这么干的：它直接写 `os.environ['MINICODE_OFFLINE']='1'` 再跑 pytest。
   → 这恰好印证了 Claude Code auto memory 文档里那条设计原则：
   **能从代码库推导出来的东西不必记**。我的夹具违反的正是它。
2. **样本量太小、方差主导**：4 个任务 × 单次运行。凡是"第 3 个任务偶尔一次猜对"这种事，
   都能把结论翻过来。要可信至少 12 个任务 × 每个重复 3 次。
3. **L4 人工确认在非交互运行里 fail-closed 拒绝**，随机污染指标。两次跑里都出现过：
   模型试图执行 `type .env`、`python -c "..."` 这类命令 → 权限链 L3/L4 弹确认 →
   非交互环境拿不到输入 → **拒绝**（fail-closed 本身是对的）→ 记一次工具错误、
   并改变后续路径。基准里这一刀是随机砍在某一组头上的。

## 要让它可信，需要先修三件

1. **让约定真的不可推导**：把要求放到仓库之外，例如"必须存在 `~/.minicode_offline`
   文件"或"由父进程注入、且仓库里不出现该名字"；
2. **样本量与重复**：任务 ≥12、每个重复 ≥3 次，报中位数与区间而不是单次均值；
3. **基准环境关掉 L4**（或给基准用到的命令配白名单）—— 顺带暴露了一个真实工程点：
   自动化/CI 场景下，L4 fail-closed 会把合法命令也拒掉，需要一个"非交互模式"开关。

## 现在的结论（对外只讲这些）

- **能讲的**：端到端对照（`memory_e2e_evidence.md`，真模型跨进程）—— 带注入能答出
  跨会话约定，关掉注入答不出；召回守门数字（注入 top-1 0.90 / top-3 0.95、反例零漏）。
- **还不能讲的**：任何"记忆让回合数下降 X%/错误数下降 Y%"的说法 —— 这一版消融支撑不了。
- **方法论收获**（面试可讲）：我做了消融，第一版两组零差异，查出来是"约定可从仓库推导"
  —— 也就是说**记忆的价值集中在"不可从代码推导"的信息上**；第二版仍被方差和 L4 的非交互
  拒绝污染，所以我把它标成"不可用"，而不是拿一个好看的数字去讲。

## 第三版：修掉三个设计问题之后（2026-10-07 重跑）

三处修正：

1. **让约定真的不可从仓库推导**：仓库**主动误导** —— `README.md` 和 `Makefile` 都指向坏掉的
   测试入口（`make test` → 直接 `pytest`，不准备环境），真正的入口 `run_tests.py` 只有
   团队约定里说。这样"知道约定"才有价值。
2. **样本与重复**：4 个任务 × 2 次重复（8 次/组），并报中位数与区间。
3. **基准里关掉 L4**：新增显式开关 `MINICODE_AUTO_APPROVE=1`（`capabilities/security.py`
   的 `_request_approval`，默认关闭、行为不变，只有显式打开才自动放行并打印警告）。
   这一条本身是个真实的工程发现：自动化/CI 场景下 L4 没人可问，fail-closed 会把**合法命令**
   也拒掉，随机污染指标。

### 结果

| 组 | 平均回合 | 中位回合 | 区间 | 工具错误 | 通过 | token |
|---|---|---|---|---|---|---|
| 不带记忆 | 5.5 | 6.0 | (4, 6) | 1 | 7/8 | 15,740 |
| 带记忆 | **4.9** | **5.0** | (2, 6) | **0** | **8/8** | **14,870** |

差值：平均回合 −0.6、中位回合 −1，工具错误 −1，通过 +1，token −870。

### 怎么读这组数（别过度解读）

- **方向一致**：带记忆在四个指标上都不差于对照组，且通过率、工具错误、token 都更好；
- **但差异小、区间重叠**（(4,6) vs (2,6)），而且两边都常撞到 `max_turns=6` 的上限 ——
  **够不上"显著"，不能对外写"回合数下降 X%"**；
- 对照组 7/8 也能做对，说明**强模型自己会调试**（读 conftest → 自带环境变量 → 重跑）：
  记忆省下的是"摸索的那一两轮"，不是"能不能做对"。

### 还想更可信的话

- 重复次数提到 ≥3、`max_turns` 提到 ≥10（现在两边都被上限截断，差异被压平）；
- 任务面铺开：现在 4 个任务全是"跑测试"的同义改写，只测了一条约定。要多条约定 × 多种任务；
- 组间配对：同一任务在两组各跑一次并**成对比较**，比两组均值更能压住方差。

## 第四版：重复 3 次、max_turns 提到 10（结论仍然只有"方向一致"）

| 组 | 平均回合 | 中位回合 | 区间 | 工具错误 | 通过 | token |
|---|---|---|---|---|---|---|
| 不带记忆 | 6.0 | **6.0** | (4, 9) | 1 | 11/12 | 17,890 |
| 带记忆 | 5.8 | **6.0** | (4, 8) | **0** | **12/12** | 18,732 |

差值：平均回合 −0.2、**中位回合 0**、工具错误 −1、通过 +1、token **+842（带记忆反而多）**。

**所以：四版跑下来，"回合数下降"这个说法始终不成立。** 唯一稳定的是
**通过率不降、工具错误不增**（这版是 12/12 与 0 错误），以及一个反复出现的现象：
强模型自己会调试（读 conftest 就知道要自带环境变量），记忆省下的是摸索的那一两轮，
而这"一两轮"被任务本身的方差（区间 4~9）完全淹没了。

### 四版汇总（供对照，别再重复踩）

| 版本 | 设置 | 结果 | 判定 |
|---|---|---|---|
| v1 | max_turns=5，约定写在报错里 | 0/4 → 2/4 | 不可用（约定可推导） |
| v2 | max_turns=8，报错不含变量名 | 2/4 → 3/4，错误 0 → 2 | 不可用（方差 + L4 随机拒绝） |
| v3 | 仓库主动误导 + 2 次重复 + 关 L4 | 5.5/6.0 → 4.9/5.0，错误 1 → 0，7/8 → 8/8 | 方向一致，不显著 |
| v4 | 3 次重复 + max_turns=10 | 6.0/6.0 → 5.8/6.0，错误 1 → 0，11/12 → 12/12 | **仍不显著** |

### 这件事的结论（可以直接讲的那句）

**"记忆有没有用"在我这个沙箱里测不出显著收益 —— 因为强模型能从仓库里把约定重新推导出来。
记忆的价值集中在"不可推导"的信息上**（团队约定、外部环境、历史决策），而这恰好是
Claude Code auto memory 文档明确说的"跳过能从代码库推导的东西"。
所以我对外只讲：跨会话能答出约定（端到端对照）、召回守门数字（top-3 0.95、反例零漏）、
以及"记忆没有让任何指标变差"；**不写"回合数下降 X%"**。
